# 结构化验收与关键用例

最终验收必须回答两个问题：测试实际执行了什么，以及必须验证的行为是否通过。pytest 退出码为 0、日志含有 `passed` 都不足以回答第二个问题。

## 运行链路

1. runner 在工作副本之外创建本轮专用目录，显式加载随项目提供的 pytest 记录插件。
2. 插件记录 pytest 完整 node ID、setup/call/teardown 结果、跳过和预期失败、被筛除的节点及收集错误。
3. 宿主读取最多 2 MB 的报告，核对 schema、本轮 run ID 和退出码。缺失、格式错误、旧报告都拒收，日志计数不再作为通过依据。
4. 每个测试集至少有一个真正 passed；所有已选中节点都要完成，setup/teardown 错误、xpass、失败和未执行不能通过。可选用例允许 skip/xfail。
5. 仓库配置中的关键节点必须全部得到 passed。缺失、被 `-k` 排除、跳过或 xfail 都拒收；参数化用例必须填写包含 `[参数ID]` 的完整节点名。
6. 验收与回归分别保存 `test_evidence` 和 `policy`，工作台显示节点、计数与拒收原因。原始日志仍可展开。生成复现沿用同一 runner，但仍不是独立验收依据。

开发阶段同样要求有效报告和实际通过用例；测试证据仍绑定源码版本与摘要。继承自宿主的 `PYTEST_ADDOPTS` 被移除，仓库自己的 pytest 配置仍生效，因此关键清单能发现项目配置过滤掉用例的情况。

## 配置示例

```json
{
  "required_acceptance_tests": ["_acceptance/test_contract.py::test_boundary"],
  "required_regression_tests": ["tests/test_module.py::test_existing_behavior"]
}
```

外置验收复制到验证副本的 `_acceptance/`。没有外置验收时，验收阶段复用开发测试，清单使用其原始相对路径。配置可以通过 CLI profile、API 或工作台接入仓库的“高级设置”填写。原来的 profile 仍兼容：缺省为空清单，并不自动推断业务上的关键测试。

三个内置修复样例均明确列出了全部外置验收和回归节点。可以用 `python -m pytest --collect-only -q` 核对节点名称，参数化用例使用稳定的显式 ID。

## 如何复验

```sh
uv run pytest tests/test_verification.py tests/test_test_evidence.py tests/test_workflow.py -q
uv run python scripts/evaluate_offline.py --backend local --allow-local --output .data/demo-evidence.json
```

覆盖：可选跳过允许、关键跳过拒收、关键节点缺失、配置过滤、全部跳过/xfail、xpass、teardown 失败、仅收集未运行、无报告但打印成功日志、旧报告以及 Windows/Linux runner。

## 边界

报告解决执行完整性与可追溯性，不证明测试断言的业务正确性，也不是防恶意 Python 伪造报告的安全边界。插件和测试在同一 Python 进程内；可信本地模式能接触宿主文件系统。Docker 通过只读源码/插件挂载、专用报告写目录、禁网和资源限制缩小执行范围，仍不承诺完整沙箱安全。

关键清单必须由任务维护者依据行为契约设置。未列出的可选测试可以跳过；不能将“清单全部通过”扩大为“所有业务行为正确”。历史任务没有结构化报告时，界面明确显示历史记录，不替其补造证据。
